Notifications — Design

In-app notification system for Riman HR

Data Model

model Notification {
  id        String   @id @default(cuid())
  userId    String
  type      String   // "LEAVE_SUBMITTED" | "LEAVE_APPROVED" | "LEAVE_REJECTED" | "ONBOARDING_TASK" | "OFFBOARDING_TASK" | "GENERAL"
  title     String
  message   String?
  link      String?  // relative URL to the related resource
  isRead    Boolean  @default(false)
  createdAt DateTime @default(now())

  user User @relation(fields: [userId], references: [id], onDelete: Cascade)
}

Triggers (existing flows → notification)

Action Recipient Link

Approach Comparison

A: Simple + Polling (Recommended)

  • Server action creates notifications inline with existing actions
  • Client polls every 30s via a lightweight API route
  • Notification dropdown in header + full list page at /notifications
  • Mark read / mark all read

Pros

  • Simple to add
  • No WebSocket infra
  • Works with existing server actions

Cons

  • 30s delay
  • Polling overhead

B: WebSocket + SSE

  • Real-time push via Server-Sent Events
  • Dedicated notification service
  • Instant delivery

Pros

  • Real-time
  • No polling

Cons

  • Complex infra
  • Overkill for 5 employees

Recommendation: A — polling is fine for a 5-person atelier
